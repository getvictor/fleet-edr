# Tasks

- [x] A stored document records whether it was shipped with the product or written by an operator.
- [x] Provenance is RECORDED when the document is stored, never derived from its path. #873 established that a rule's identity is its file stem rather than its path, and widened the load to walk the whole stored set precisely so authored content need not live under `imported/`. A prefix rule would contradict that and be chosen by the operator it describes: writing to `imported/mine.yml` would launder an authored rule into a vendored one, and a Detection Rule License attribution with it.
- [x] A caller cannot declare its own provenance through the AUTHORING surface: that write records the operator's source itself, because how a document arrived is an observation rather than a claim. A whole-corpus replacement may state it, and must, since that is the path a pack upgrade and a restore go through and both have to put an operator's rules back as theirs rather than relabelling them.
- [x] Writing over a shipped document makes it the operator's, since the bytes are now theirs.
- [x] Attribution follows the recorded source: an operator's rule is credited to their deployment, a shipped rule keeps crediting upstream and its author. Asserted where it becomes visible, with fixtures that share a path prefix and an `author:` field so ONLY the recorded source distinguishes them.
- [x] The consequence that reaches persistence is covered too: `AlertOriginOf` is what every alert row stores, so a wrong credit there is durable and much harder to walk back than a catalog label.
- [x] The corpus records which shipped pack it holds, as a digest over the shipped content. Derived rather than declared, because a hand-maintained version has to be bumped by whoever edits the corpus and forgetting is silent: the deployment believes it is current while running different rules.
- [x] The digest covers the vendored half only, so an operator adding a rule does not make a deployment look out of date, nor deleting one make it look current.
- [x] The digest is recorded in the SAME transaction as the content it describes. Written separately it could fail on its own and leave a corpus whose content and stated identity disagree, silently.
- [x] Migration defaults existing rows to vendored, which is a statement of fact rather than a guess: every document predating this was written by the seed, since the authoring surface shipped after it and the only other writer had no production caller.
- [x] Mutation-tested across rounds; the running total and what each round found is recorded in the final entry below. Two survived the first pass and both were weak TESTS rather than weak code: the pack-identity test drove `PutDocument`, which at the time recorded no digest at all, so it passed whatever the filter did (round 1 later made that path recompute, which would have masked the gap rather than closing it); and the "document moved" fixture changed sort order as well as path, so it would have passed with the path removed from the hash entirely.
- [x] Real-tool QA on the dev server. An authored rule was written deliberately to `imported/qa_provenance.yml`, the laundering path this change exists to close, and carrying an `author:` field naming someone else: it was recorded `authored` and credited `Locally authored` in the catalog, so neither the directory nor the rule's own text moved the credit. The migration was applied against the populated dev corpus, defaulting its 69 existing documents to vendored. For the durable half both that rule and a shipped one were put in alert mode and matched by ONE event on ONE host in ONE batch, raising two alert rows: `Locally authored` and `SigmaHQ, by Alejandro Ortuno, oscd.community`. Same event and same batch, so the recorded source is the only thing that separates them.
- [x] An unrecognised provenance is refused on the way in and on the way out. `Source.Valid` existed, and its own comment said a reader must not silently treat an unknown value as either known one, but nothing called it. The asymmetry is what makes it worse than either: an unknown value is not authored, so attribution credits it upstream, and it is not vendored, so the pack digest leaves it out. One such row would carry a licence claim about content nothing here can vouch for.
- [x] The pack identity follows a single-document mutation, not just a whole-corpus write. Writing over a shipped document reclassifies it as the operator's and deleting one removes it, so both change the shipped set while looking like they do not. Recomputed in `withVersionBump` for the reason the version bump lives there: neither mutation can forget it.
- [x] The operator's own rules are excluded from the alert-origin backfill (#870). Because a rule's id is its file stem, an operator who writes their own version of a shipped detection keeps that id, and crediting its historical alerts to them would permanently claim they wrote a detection they did not. That is this feature's failure mode pointed the other way, so the backfill deny-lists the local origin alongside the project's own.
- [x] The migration is forward-only, per ADR-0009. The Down section dropped both columns, which is worse here than the policy alone says: re-running the Up would recreate every surviving row defaulted to vendored, so an operator's rules would be credited upstream again. That is exactly the misattribution this migration ends, and it is not recoverable from the migration itself. `00012_alerts_origin.sql` is the precedent, a no-op Down for the same reason.
- [x] The backfill's third exclusion is in the spec that owns the requirement, not in this change's delta. Two in-flight deltas modifying one requirement is the collision that silently drops scenarios at archive time, so the scenario was added to `backfill-alert-attribution`, which still owns it until the release archive runs.
- [x] `Document.Source`'s contract was corrected rather than restated. It claimed a caller never declares provenance, which is true of the authoring surface and false of the whole-corpus replacement the pack upgrade and a restore both go through: those must be able to put an operator's rules back as theirs rather than relabelling them.
- [x] The persisted digest FORMAT is pinned against literal bytes. Every other assertion here compared `PackDigest` to another call to `PackDigest`, which holds under any change to the framing, the field order, or the hash: the one property that matters is that a LATER build computes the same value for the same content, and no self-comparing test can state it. Dropping the length prefix, the path, or the sort each survived the old tests and each fails the golden one.
- [x] The legacy unknown-identity state is in the spec and under test. A corpus stored before this existed reports NO identity, which has to stay distinguishable from the identity of a genuinely empty pack: the first means "unknown, therefore not known to be current" and the second is a real answer.
- [x] Every consumer-facing description of the origin values names all three. This took two passes and the first one is the lesson: enumerating only Go and Markdown found five sites and read as complete, while the OpenAPI spec (both copies) and the UI's own types were never searched and still described two. The enumeration is now over every tracked file rather than over the file types that came to mind: the webhook contract, the generated rule reference via its generator, `RuleMetadata.Origin`, the operator listing's response, `Origin`'s own method comment, the persisted alert field's contract, `docs/api/openapi.yaml` and its embedded copy, `ui/src/api.ts`, and `ui/src/types.ts`.
- [x] The externally visible attribution and the stored provenance values are pinned as LITERALS. Every other assertion about them compared a constant with itself, so a rename would pass all of them: for `LocalOrigin` that silently changes what every alert row and API response carries, and for the source values it is worse now that an unrecognised source is refused on read, since every row an earlier version wrote would stop being interpretable and the whole corpus of every existing deployment would fail to load. Changing any of those strings is a migration, and these are where that has to be noticed.
- [x] Both production LOAD seams are pinned, and they were the real gap. The provenance argument passed at startup and at reload was covered by nothing: reverting either to `nil` left every test green while crediting an operator's rule to SigmaHQ on every restart and at every publish, which is the whole bug this change fixes. The fixtures carry `author: test`, so losing the wiring does not produce a neutral value but an upstream credit. This is the failure mode that mutation testing exists to catch and that testing only the GUARDS misses: fifteen mutants had all been guards and formats, not wiring.
- [x] The validator's seam is deliberately unpinned, and says so. Nothing it reports depends on who wrote a rule, so a mutant replacing that argument survives; the true value is passed anyway because `nil` is not "unused" there, it is the false claim that every document is vendored.
- [x] The rolling-upgrade question is answered with evidence rather than asserted. A column added with a DEFAULT is a hazard whenever an old replica still writes the table without naming it, which would record an operator's rule as vendored during cutover. It cannot happen here because no released binary writes this table at all: `rule_corpus_documents` is absent from v0.4.0 and v0.4.0-rc.1, and the table, its store, and `PutDocument` all arrived in a commit that is in no release tag. It stops being moot after this release, and the migration says so.
- [x] The pack digest is re-derived only when the SHIPPED set actually moved, which the common case does not: an operator adding or editing a rule of their own leaves the pack alone. The first version rescanned on every mutation and justified it by claiming that deciding whether the set moved meant reading the documents anyway. That was false and review was right to say so: the answer comes from the one row being written. The cost was real, not theoretical, because the rescan materialises every document inside the transaction holding the meta row's `FOR UPDATE`, which serialises every mutation of this corpus: at the validator's own bound of 4096 documents times 64 KiB that is 256 MiB read under the one lock every other writer waits on.
- [x] The migration is exercised against a corpus that already holds documents, which nothing repeatable did before: every other test opens an already-migrated database, so this was covered only by the dev-server QA. The test rewinds by dropping the columns and the migration's version row and re-applies the schema, so goose replays the checked-in file rather than a copy of its DDL. Defaulting the rows to `authored` and destroying them are both caught.
- [x] Mutation-tested, twenty-three mutants. Twenty-one caught. Two survive by design and are documented rather than papered over: the validator seam, whose output does not depend on who wrote a rule, and recomputing the digest unconditionally, which produces the same identity and only costs more.
