# Tasks

- [x] Installing the build's pack is separate from seeding, because the seed's empty-corpus guard is load-bearing and cannot be relaxed: a seed that ran on every boot would overwrite an operator's work.
- [x] Only the shipped half is replaced. An operator's own rules survive an upgrade.
- [x] A path the operator has taken over stays theirs. Writing over a shipped rule makes that document theirs, so a pack still shipping that path must not quietly take it back.
- [x] A pack declaring authored content is refused. A pack is shipped content by definition, so a document in one claiming to be the operator's is a contradiction, and accepting it would install rows nobody authored that carry no upstream credit.
- [x] Installing is idempotent, compared as "what this pack would store" against "what is stored" rather than build-pack against recorded-digest. The naive comparison reinstalls on every boot on any deployment that has overridden a shipped rule.
- [x] A build shipping no rule documents leaves the stored pack alone. Seeding treats an empty source as a legitimately empty corpus because there is nothing to lose; here there is, so the only safe reading is that the build is wrong rather than that the pack is deliberately empty.
- [x] Tuning survival is asserted across the two contexts that make the claim true, not assumed from where the tables sit. Nothing in either context announces the dependency, so a later change to where tuning lives would break it silently, on upgrade, on a deployment that had tuned deliberately.
- [x] The startup WIRING is pinned, not just the operation. The fixture pre-loads a pack this build does not ship, so the seed declines and only the upgrade can reconcile it; starting from an empty database would install the build's pack through the seed and pass whether or not the upgrade were wired at all.
- [x] Mutation-tested, six mutants, all caught, including deleting the startup call.
- [x] Real-tool QA on the dev server, against a deliberately stale pack: one shipped document mutated, another deleted, an operator's own rule added, a shipped path taken over by the operator, and a rule tuned to alert/critical. Starting the server installed the build's pack: the deleted rule came back, the mutation on the un-overridden document was reverted, the operator's own rule survived as theirs, the path they had taken over kept THEIR edit and stayed authored, and the tuning was untouched. Restarting then wrote nothing and left the version at 22, which is the case that matters: that deployment holds an override, so a comparison of the build's pack against the recorded digest would have reinstalled on every boot.
