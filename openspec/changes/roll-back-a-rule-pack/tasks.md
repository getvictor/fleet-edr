# Tasks

- [x] The generation an upgrade replaces is retained, in the same transaction as the replacement. Written separately it could fail on its own and leave a corpus whose "previous" is a generation that was never actually replaced, which is worse than having none: a rollback would then install the wrong thing.
- [x] One generation, replaced wholesale. A history needs a retention policy, a way to name a generation and a way to choose between them, and restoring the set just replaced is what makes a bad upgrade survivable.
- [x] A rollback survives the next restart. Without a record of the refusal the upgrade would reinstall the rejected pack on every start, since after a rollback "what this pack would store" and "what is stored" differ by construction. The operator's only recourse would be never to restart.
- [x] Declining is keyed on the PACK, not a boolean. A latch would leave an operator needing to remember to switch upgrades back on, and forgetting is silent; the next release ships a different pack and installs normally.
- [x] The operator's own rules survive a rollback, including ones written after the upgrade being rolled back. Rolling back a pack restores shipped content; it is not an undo of their edits.
- [x] A rollback with nothing retained is reported rather than restoring an empty set, which would leave the deployment detecting nothing while reporting success. That is the ordinary state of a deployment that has never upgraded.
- [x] A second rollback is refused rather than "restoring" the generation already installed, because the retained one was consumed by the first.
- [x] Installed-versus-available is reported by RULE identity, not by path: that is what an operator recognises and what their tuning is keyed on, and a rule that moved directories upstream would otherwise read as one removed plus one added.
- [x] The operator's own rules are excluded from that comparison, so writing one does not make a deployment look out of date. Same property the pack digest carries, and the same reason.
- [x] Mutation-tested, five mutants, all caught: a declined pack reinstalling, nothing being retained, an empty rollback reporting success, a second rollback re-restoring the live generation, and a rollback failing to record the decline.
- [x] Real-tool QA against the dev database, with its populated 69-document corpus and the migration applied to it in place. Installing a deliberately different pack left 1 shipped document and retained 69; rolling back restored all 69 and recorded the decline; running the startup install again changed nothing and left the version at 26, which is the case the decline exists for; a second rollback was refused. The operator-facing HTTP for this lands with the surface that closes #768, so the lifecycle was driven through the same bootstrap the server calls rather than through a route that does not exist yet.
