# Tasks

- [x] The generation an upgrade replaces is retained, in the same transaction as the replacement. Written separately it could fail on its own and leave a corpus whose "previous" is a generation that was never actually replaced, which is worse than having none: a rollback would then install the wrong thing.
- [x] One generation, replaced wholesale. A history needs a retention policy, a way to name a generation and a way to choose between them, and restoring the set just replaced is what makes a bad upgrade survivable.
- [x] A rollback survives the next restart. Without a record of the refusal the upgrade would reinstall the rejected pack on every start, since after a rollback "what this pack would store" and "what is stored" differ by construction. The operator's only recourse would be never to restart.
- [x] Declining is keyed on the PACK, not a boolean. A latch would leave an operator needing to remember to switch upgrades back on, and forgetting is silent; the next release ships a different pack and installs normally.
- [x] The operator's own rules survive a rollback, including ones written after the upgrade being rolled back. Rolling back a pack restores shipped content; it is not an undo of their edits.
- [x] A rollback with nothing retained is reported rather than restoring an empty set, which would leave the deployment detecting nothing while reporting success. That is the ordinary state of a deployment that has never upgraded.
- [x] A second rollback is refused rather than "restoring" the generation already installed, because the retained one was consumed by the first.
- [x] Installed-versus-available is reported by RULE identity, not by path: that is what an operator recognises and what their tuning is keyed on, and a rule that moved directories upstream would otherwise read as one removed plus one added.
- [x] The operator's own rules are excluded from that comparison, so writing one does not make a deployment look out of date. Same property the pack digest carries, and the same reason.

- [x] Real-tool QA against the dev database, with its populated 69-document corpus and the migration applied to it in place. Installing a deliberately different pack left 1 shipped document and retained 69; rolling back restored all 69 and recorded the decline; running the startup install again changed nothing and left the version at 26, which is the case the decline exists for; a second rollback was refused. The operator-facing HTTP for this lands with the surface that closes #768, so the lifecycle was driven through the same bootstrap the server calls rather than through a route that does not exist yet.
- [x] A rollback does not take back a rule the operator has taken over since the upgrade. Review caught this and it has two shapes with one cause: at the same path the restore is a duplicate-key failure that aborts the whole rollback, and at a different path with the same identity it stores two documents for one rule, which makes the corpus refuse to load and takes every rule on the deployment down. The install path already filtered for exactly this; the restore now uses the same filter, and reports what it withheld.
- [x] The declined pack is read from what the UPGRADE recorded, not from the build the replica serving the request happens to run. During a rolling deployment those differ, and a rollback served by an older replica would otherwise decline that replica's pack and leave the newer one free to reinstall on the next start.
- [x] The retained generation's identity is derived from the snapshot rather than copied from `pack_digest`, which is deliberately empty on a corpus predating provenance. Copying it left the first upgrade on such a deployment retaining rows while reporting no generation to roll back to, so the status surface said rollback was unavailable while the rollback itself worked.
- [x] Pack status reads the meta row and the documents in ONE transaction. Assembled from two reads it can describe two generations: an upgrade committing between them yields the old installed digest beside the new documents, reporting "not current" with every diff list empty, which is a nonsense answer rather than a stale one.
- [x] Two Source-normalising helpers were deleted rather than merged. Review noticed both were duplicates AND that neither could have had an effect: `PackDigest` hashes the path and the content, never the source, so marking it on a copy first changed nothing. The pack is digested as given.
- [x] The release note was withdrawn from this change. It told operators they could roll back, and nothing in this PR can invoke a rollback; it belongs with the surface that makes it reachable.
- [x] The runs of writes go through one accumulating writer rather than a `return err` after every line. Ten copies of that block for two operations meant ten error branches no test can reach without injecting a database fault, and the call sites now read as the ordered list of writes they are, which is the part worth checking by eye. Installing and rolling back also share the one write sequence, since they are the same three steps and had a copy each: two places for the ordering to drift.
- [x] Mutation-tested, seven mutants, all caught: a declined pack reinstalling, nothing being retained, an empty rollback reporting success, a second rollback re-restoring the live generation, a rollback failing to record the decline, a rollback taking back a rule the operator now owns, and the retained generation being left with no identity. That last one SURVIVED at first: the fix was made and nothing pinned it, which is what the run is for.
- [x] New-code coverage measured the way CI measures it: 80.8%, from 71.9%. The remaining uncovered lines are database-error propagation reachable only by fault injection; every branch that a caller can actually reach is exercised, including reading status and rolling back against a row whose provenance this version cannot interpret.
