# Tasks

- [x] A boot-time pass credits alerts whose origin was never recorded, for vendored rules only, under `DoOnceIfLeader` so exactly one replica runs it and none waits.
- [x] Our own rules are excluded, so the distinction migration 00012 preserves between "raised before attribution existed" and "raised by us" survives.
- [x] Projections are excluded, so this project does not claim authorship of an operator's own policy entry.
- [x] The scope decision is a named function with its own tests, because both exclusions are invisible in the SQL and irreversible if wrong. Mutation-tested: dropping either exclusion, or reading `OriginOf` instead of `AlertOriginOf`, is caught.
- [x] Only rows with an empty origin are touched, so an attribution already recorded is never overwritten and a second pass is a no-op. Both are pinned, and mutation-tested.
- [x] A deployment running no vendored rules issues no statement at all, rather than a malformed one with no branches.
- [x] A failure is logged and does not stop the server, and the pass runs in the BACKGROUND so it does not delay the replica becoming able to serve. Its cost scales with alert history, nothing a request can observe waits on it, and a rolling restart would otherwise pay that cost once per replica. Shutdown cancellation is not logged as a failure, since that would put a warning in the log of every deployment restarting mid-pass.
- [x] The rewrite is batched and walks the primary key from a cursor, because alerts carries no index this predicate can use (rule_id sits third in the dedup key, behind source and host_id). An unbounded rewrite would hold row locks across a table scan at boot; a bound alone would have been worse, since with no usable index every statement restarts the scan and N batches cost N scans. Resuming from the last id keeps the scan single while the locks stay bounded. The loop is covered by seeding one more row than a batch holds. Two mutants are knowingly missed and were measured, not assumed: raising the bound, and pinning the cursor at 0. Each batch's update removes its rows from the predicate, so the loop terminates correctly either way, and total scan work is not observable from a functional assertion. Dropping the empty-origin guard, which is the correctness property, IS caught.
- [x] Alerts from a rule the deployment no longer runs stay uncredited, and that limit is stated rather than worked around.
