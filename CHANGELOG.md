# Changelog

Notable changes to Fleet EDR, newest first. This project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html) (pre-1.0).

## [0.4.0] (2026-07-07)

Feature release on top of 0.3.0. The headline is a re-architected event store: raw telemetry now lives in a ClickHouse archive backed by a small MySQL work queue, which unlocks fleet-wide hunting (process, connection, and DNS search), a host event timeline, and a flexible time-navigation control across the investigation surface. Also in this release: a unified principal model that makes every service-account action fully attributable, the groundwork for Windows agents (a platform-tagged event contract, a driverless ETW process sensor, and platform-scoped detection rules), agent health reporting on the Hosts page, and detection-reliability fixes that close a concurrent-processing race which could silently drop alerts. Read the upgrade notes below before upgrading: `EDR_CLICKHOUSE_DSN` is now required, and the `EDR_OIDC_*` SSO seeding variables are removed.

### Upgrade notes (action required)

- **The event store is now ClickHouse.** The server stores raw events in a ClickHouse archive (durable history + per-process correlation) and a small MySQL work queue (the processing backlog), instead of a single MySQL `events` table. `EDR_CLICKHOUSE_DSN` (or `EDR_CLICKHOUSE_DSN_FILE`) is now **required**: the server and the standalone ingest service refuse to start without it. Stand up a ClickHouse instance alongside MySQL and point both binaries at it. The reference operator compose stacks (`docker-compose.quickstart.yml`, `docker-compose.prod.yml`, and the multi-replica stack under `packaging/`) now provision a ClickHouse service and point the server at it via a `clickhouse_dsn` secret, so a stack brought up from them needs no extra ClickHouse wiring. This is a hard cutover with no data migration: pre-upgrade event history is not carried over (alerts and their self-contained evidence are preserved). MySQL still holds the control plane (process graph, alerts, hosts, settings).
- **The `EDR_OIDC_*` SSO environment variables and `EDR_AUTH_ALLOW_NO_OIDC` are removed.** SSO is configured entirely through the Single sign-on settings screen (the in-product path since 0.3.0), so the env-var seeding path and the boot gate it fed are gone. The server now always boots without OIDC configuration and is configured at runtime via the UI after a break-glass sign-in. Existing deployments are not stranded: the `EDR_OIDC_*` variables already seeded the durable `oidc_config` store on first boot under 0.3.0, and that stored configuration remains the source of truth. Setting `EDR_OIDC_ISSUER`, `EDR_OIDC_CLIENT_ID`, `EDR_OIDC_CLIENT_SECRET` (and `_FILE`), `EDR_OIDC_REDIRECT_URL`, `EDR_OIDC_ALLOW_JIT_PROVISIONING`, `EDR_OIDC_DEFAULT_ROLE`, or `EDR_AUTH_ALLOW_NO_OIDC` is now inert (ignored at boot, not an error). Configure SSO under **Admin settings -> Single sign-on**.

### Added

- **The signed-in email is no longer shown in the top-right bar.** The account menu's collapsed trigger now shows only the avatar initial (and the break-glass badge when applicable); the full email is revealed only when the operator opens the dropdown. This keeps the operator's account from being passively disclosed to anyone viewing the screen or a screen-share, while leaving it one click away for a deliberate "who am I signed in as" check. The break-glass badge is also restyled to a solid gold pill so it is legible on the dark nav bar.
- **Alert triage lives on the alert header, not the process node inspector.** On an alert's page, the alert detail surface now shows the alert's status and its acknowledge / resolve / reopen controls, and its MITRE technique tags link to the rule doc. This is the single triage surface, so a process-optional alert (no process node to select) can finally be acknowledged or resolved from the page. The process detail panel no longer restates the alert (severity, description, lifecycle buttons) that the header already shows; it lists the process's alerts as compact links to the alert page, keeping the per-alert technique tags. The panel's evidence rows also align their copy and fleet-search affordances into one trailing icon column, the fleet-search pivot becomes an icon, and the panel widens to fit.
- **The alert scope now follows into the timeline.** When the host page is opened for an alert, the "Alert chain / Full tree" toggle drives both views: the timeline scopes to the alert chain (the alerted process plus its ancestors and descendants) instead of showing every host event, and switching to Full tree widens it back. `GET /api/hosts/{host_id}/timeline` gains an optional `chain` filter of process generations (`pid:pidversion`); an event matches only when both its pid and its kernel pid generation (pidversion) match, so heavy PID reuse (a pid held by several processes over a window) does not pull unrelated processes' events into the scope. Previously the alert focus applied only to the graph, so switching to the timeline dropped the scope and showed the whole host stream.
- **Inline MITRE ATT&CK technique tags.** Technique ids are now shown where the investigation happens, not only on the alert breadcrumb: an alerted process node's hover tooltip lists its techniques (display-only), the process detail panel shows each alert's techniques as badges linking to the rule's documentation page, and a host-timeline row whose event triggered an alert carries that alert's technique tags (linked to the rule). The timeline tags key on the alert's triggering event ids, so the technique appears on the exact event that fired it. No server change: every technique id was already on the alert payload. Completes #585.
- **Host event timeline tab.** The host page gains a **Timeline** view beside the process graph (the active view lives in the URL, so it is bookmarkable and the shared time window and alert anchor survive a switch). The timeline renders the host's exec, network, and DNS events for the active window as a flat, newest-first table, filterable by event-type chips and a text box, with keyset "Load more" paging and a match count, over the same compact time control and activity histogram as the graph. Cross-links run both ways: a timeline row opens its process in the graph (anchored at the event, selected by pid and time), and a process node's detail panel gains a "Show in timeline" link that emphasizes that process's rows; connection and DNS rows carry the same fleet-wide "search" pivot as the detail panel. Completes #583.
- **Host event timeline endpoint.** A new `GET /api/hosts/{host_id}/timeline` returns one host's exec, network-connection, and DNS-query events interleaved in event-time order (newest first) over an event-time window, filterable by event type and a case-insensitive payload text match, keyset-paginated with a `total_matched` count like the fleet-wide search. All three classes already live in the ClickHouse archive, so the query merges them natively; the window bounds event time (what the host page's time control means), and rows carry the originating pid for the graph cross-link. Server half of #583 (the "flat, filterable list beside the graph" pattern); the Timeline tab UI follows.
- **Connection and DNS search modes with network pivots.** The Search page gains Connections and DNS modes alongside Processes (the mode lives in the URL, so each is bookmarkable). Connection mode scopes a remote address, DNS mode a domain, both fleet-wide over the ClickHouse archive with the same "Load more" paging and "N of M" count as process search; because the endpoints require an artifact, each event mode prompts for the address or domain rather than firing an empty search, and an optional host chip narrows either to one host. Event rows show the host, originating process, and the mode-specific detail (direction/protocol/remote endpoint for connections; query type and resolved addresses for DNS). The process detail panel's network section gains a "search fleet" pivot on every remote address and DNS name, so "who else talked to this IP / resolved this domain" is one click. Completes #582.
- **Search page and host-page search pivots.** A new **Search** page (nav entry, gated on process read) puts the fleet-wide process search behind a UI: removable filter chips for host, path, SHA-256, uid, and signing verdict; a results table with resolved host names, command lines, and verdicts; keyset "Load more" paging with a running "N of M" count; and rows that pivot into the host's process tree. The process detail panel gains "search all hosts" links next to the path, hash, uid, and signing verdict, so an analyst pivots from one process to the whole fleet in one click. First UI half of #582; the connection/DNS search modes and their network pivots follow.
- **Fleet-wide connection and DNS search.** Two new endpoints, `GET /api/search/connections` and `GET /api/search/dns`, answer the cross-host network-scoping questions ("who else connected to this IP", "who else resolved this domain") over the ClickHouse event archive, with the same keyset-cursor + `total_matched` contract as the process search. The archive gains materialized `remote_address` and `query_name` columns with bloom-filter skip indexes so a fleet-wide lookup prunes granules instead of scanning. Second of #582's three PRs; the search UI and host-page pivots follow.
- **Fleet-wide process search.** A new `GET /api/search/processes` endpoint answers the cross-host hunting questions the per-host tree cannot: filters (host, path, SHA-256, uid, fork-time window, exit reason, and code-signing verdict) compose in SQL, results are newest-first with keyset cursor pagination that stays correct as new processes arrive, and each response carries `total_matched`. Searching a hash with no host returns matches from every host; adding a host filter scopes the same query to one. This is the server half of the global hunting console (issue #582); the network/DNS artifact classes and the search UI follow.
- **Time navigation on the host page.** The four fixed range buttons are replaced by one compact control: a labeled button ("Last 1 hour" or an absolute span) whose popover offers relative quick-picks (now up to 7 days) and an absolute from/to picker, with arrows that shift the window by its own width. An activity histogram above the tree shows process starts per time bucket for the active window (server-aggregated, so it stays honest even when the rendered tree is capped), and clicking a bucket narrows the window to that spike. Alert deep-links keep their wide window anchored at the alert time. Backed by a new `GET /api/hosts/{host_id}/activity-histogram` endpoint.
- **Conviction evidence on the process tree.** Hovering a node now shows the process's full command line and a derived code-signing verdict (Apple platform, Developer ID with the team id, ad-hoc, signed, or unsigned), so an analyst reads an ancestry chain without a click per node; ad-hoc and unsigned processes carry an amber ring in the graph. The detail panel replaces the raw signing id with the verdict badge plus the signing and team identifiers, and the command line, path, SHA-256, cdhash, signing id, and team id each copy in one click. Verdicts are signer categories, not notarization claims (Endpoint Security exposes signing flags and identifiers, not ticket checks), and a forked process that has not exec'd yet shows no verdict rather than a false "unsigned".
- **Host detail identity header.** The host page now opens with the host's identity instead of a raw id: hostname title, online/offline pill (the host list's 5-minute rule), OS name/version/build, agent version, last seen, source IP, event count, and enrollment date, with the raw host id kept visible and copyable for log correlation. Backed by a new `GET /api/hosts/{host_id}` endpoint. The header loads best-effort and never delays the process tree.
- **Events carry an operating-system platform (Windows support groundwork).** The event envelope gains an optional `platform` field (`darwin`, `windows`, or `linux`), the first step of the phased Windows agent in ADR-0018. Ingestion accepts a recognized value, rejects an unrecognized one (`invalid_platform_at_<i>`), and normalizes an absent value to `darwin`, so an agent predating this contract keeps working unchanged; the platform is persisted through both the work queue and the event archive. The macOS extension stamps `darwin` on every event. This is additive and changes nothing an operator sees yet; it lets the server distinguish and (in a later change) scope detection by platform.
- **Host platform in the inventory and Hosts page.** The agent reports its platform at enrollment, the server persists it on the enrollment record, and `GET /api/hosts` carries a `platform` for each host (empty for a host that has sent events but never enrolled). The Hosts page shows a Platform column (macOS / Windows / Linux, or "unknown"). Part of the Windows support groundwork (ADR-0018); the enroll endpoint rejects an unrecognized platform and defaults an absent one to `darwin`.
- **Windows process telemetry (driverless ETW sensor).** The Windows agent now collects process start/stop events by consuming the Microsoft-Windows-Kernel-Process ETW provider in user mode (no kernel driver), the first Windows sensor (ADR-0018, Phase 1). Events flow through the same enroll/queue/upload pipeline as macOS: a process start becomes an `exec` event and a stop an `exit`, stamped `platform: windows`, with the image path reported as a DOS path and the process creation time carried as `create_time_ns` (the platform-neutral pid_epoch). Command-line capture, Authenticode signing, and network/DNS providers are follow-ups.
- **Detection rules are platform-scoped.** Each detection rule now declares the operating systems it targets, and the engine evaluates a rule only against events of those platforms (a platform-less event is treated as `darwin`), so a macOS rule never fires on a future Windows event. `GET /api/rules` carries each rule's `platforms`. All current rules target `darwin`; this changes nothing for a macOS-only fleet. Part of the Windows support groundwork (ADR-0018).
- **Process tree collapses repeated sibling executions.** A busy host's process forest is dominated by repetition (`grep ×1000`, `jspawnhelper ×240` in one window). The `GET /api/hosts/{host_id}/tree` response now collapses repeated identical-path leaf siblings under the same parent into a single aggregated node carrying the member count, the exited/running split, and the fork-time span (grouped by parent, image path, and binary identity, so distinct binaries or lineages never merge). The tree UI renders these as a `×N` badge that expands in place to a sample of the underlying processes, and a new **Flatten** toggle (mirrored by a `?flatten=1` query parameter) returns the raw, un-aggregated forest for an analyst who wants every node. Aggregation is a read-time transform that shrinks the response payload itself; it neither drops nor duplicates a process and never folds a node that has its own subtree (issue #416).
- **Self-contained alert evidence.** An alert now captures the full envelopes of its triggering events at creation time, so the evidence stays readable even after the underlying events age out of retention. The alert-detail API response gains an `events` array alongside `event_ids` (see `docs/api/openapi.yaml`).
- **Agent health on the Hosts page.** The agent now reports its health as an extensible per-component snapshot through a host-token-authed `POST /api/status`, on startup, on each extension transition, and periodically; the server persists the latest state per host and rolls the components up into one per-host status (`healthy`/`degraded`/`unhealthy`/`unknown`). The Hosts list shows a per-host health badge (distinct from the online/offline pill) and the host detail shows a conditions panel with each component's status, message, and time-in-state (`GET /api/hosts/{host_id}/health`). System-extension activation (endpoint security + network extension) is the first signal, surfacing the previously invisible case of a host that enrolls but whose sensor never activates: it now reads "needs attention" instead of looking identical to a healthy host (issue #359). New signals (DNS proxy, event-queue depth, policy staleness) are agent-only additions that need no wire or UI change.

### Changed

- **Connection and DNS search open on recent events; search filters are validated.** The Search page's Connections and DNS modes now open on the fleet's most recent events of that type (like the Processes mode) and narrow once you enter a remote address or domain, instead of sitting behind a prompt until an artifact is typed. The `GET /api/search/connections` and `GET /api/search/dns` endpoints accordingly treat the artifact value as optional (absent lists recent events, newest-first) rather than returning 400. The DNS results table now shows the queried domain per row (it varies across the recent feed), and the unfiltered recent-events listing shows only the number of rows loaded rather than a fleet-wide total: computing that total is the more expensive half of the query on a large archive and adds little to a browse view, so it is skipped (a filtered search still shows the exact total). The Processes mode's default view (no filters) does the same: `GET /api/search/processes` skips the count over the whole process table and the page shows only the rows loaded, since that grand total is the query's most expensive half and adds little to a browse (any filter, even a lone host, restores the exact total). Separately, `GET /api/search/processes` now rejects a `signing` or `exit_reason` value outside its accepted set with `400` (`invalid_signing` / `invalid_exit_reason`) instead of silently applying a filter that matches nothing, so a mistyped filter is a clear error rather than an empty result.
- **Alert page cleanup: quieter agent health, no self-referential alert link, triage in the header.** Agent health moves off its standalone "Agent healthy" card into the host header's Details popover: the Details trigger carries an attention dot only when the agent is not healthy (amber degraded, red unhealthy), so a healthy host shows no health chrome, and opening the popover reveals the rollup plus each component's status, message, and time-in-state. The process detail panel's "Related alerts" list no longer links back to the alert whose page is already open (it still lists every other alert on the process). The alert's status and its acknowledge / resolve / reopen controls move into the alert header row next to the id / severity / title / time; the triage behavior is unchanged. The process tree's "Show system" toggle is now hidden when it would change nothing (for example an alert chain whose only system-path processes are the alerted process and its ancestors), instead of showing a dead control. And the process detail panel's "Kill process" button is disabled, with the reason shown, once the process has exited: a kill targets a live PID, and after exit that PID may be reused, so killing it could hit an unrelated process. The alert list's Host column now shows the host's enrollment hostname instead of the raw hardware UUID, matching the host list and search results (the UUID stays in the link tooltip); a host with no known hostname still falls back to its id.
- **Host identity stays current without a re-enroll.** The agent's status check-in now carries a host inventory block (hostname, OS name/version/build, agent version), and the server refreshes the host's identity record from it. A macOS upgrade, hostname rename, or agent upgrade is reflected in the console within about a minute, instead of being frozen at the enrollment-time snapshot until a forced re-enroll. Fresh enrollments also now record the friendly OS product version (for example `26.4`) instead of the platform token `darwin`. Older agents that send no inventory keep working; their identity simply stays enrollment-time.
- **The app now opens on Alerts.** Signing in (or navigating to the application root) lands on the alert list instead of the host list, matching the alert-first analyst workflow; an operator whose role cannot read alerts lands on the first navigation entry their permissions allow. The host list moved to its own **Hosts** page (`/ui/hosts`) with identical content, and the top navigation reordered to Alerts, Hosts, Application control, Coverage. Bookmarks to the application root now open Alerts; bookmark the Hosts page directly for the old view.
- **Service-account actions are now fully attributable (unified principal model).** Every operator action is recorded against a typed principal (a user or a service account), so a service-account-initiated change names the specific service account rather than appearing as an anonymous or failed write. Service accounts can now manage detection-config exclusions and rule-settings (previously rejected with `actor is required`), and SSO / app-config / app-control / trace-sampler mutations they make are attributed to them. The audit-log API response identifies the acting principal for every row, and per-row attribution fields (including the alert API's `updated_by`) now carry the principal id (`usr_<id>` / `svc_<id>`) rather than a bare numeric user id. The detection-config exclusions list resolves each author to a display label for any principal type: the response field `created_by_email` (user-only) is replaced by `created_by_label`, which carries a user's email, a service account's name, or `system`. See ADR-0017.
- **Events move to a ClickHouse archive + a MySQL work queue.** Ingestion durably writes each accepted event to the ClickHouse archive and enqueues it on the MySQL queue, returning success only after both; the detection processor claims from the queue. Per-process network/DNS correlation and alert evidence read the archive. Event retention is now ClickHouse-native time-based expiry rather than a periodic MySQL delete (process-record pruning is unchanged). A leader-gated sweep prunes acknowledged events from the work queue in batches so it keeps to its in-flight working set; the `edr.event_queue.rows_pruned` metric reports its throughput.
- **Operator mutation endpoints reject an oversize request body with 413.** The application-control and detection-config mutation handlers now bound the request body at their per-route cap and return `413 Request Entity Too Large` with a typed `*.body_too_large` error code (`application_control.body_too_large`, `detection_config.body_too_large`) instead of silently truncating a body past the cap (a truncated body previously surfaced as a misleading `invalid_json` 400 or, if it happened to stay valid after truncation, a partial-but-accepted mutation). Per-route caps are unchanged (application control 16 KiB per rule and 256 KiB bulk upsert; detection config 16 KiB), so a request within the documented cap is unaffected. This brings the two handlers in line with the identity admin endpoints, which already rejected oversize bodies.
- **The host and alert pages are simplified.** The host detail header now leads with just the hostname, an online/offline pill, and the OS; the raw host id, agent version, source IP, event count, exact last-seen, and enrollment date moved into a Details disclosure (the id's one-click copy control moved there too, so it no longer sits ambiguously beside the hostname), and "last seen" appears in the header only when the host is offline. The Agent health panel collapses to a single "Agent healthy" / "Agent needs attention" pill when the rollup is healthy and reveals the per-component rows on demand; they still show automatically when something needs attention. The alert view's chain toggle is now a two-option segmented control ("Alert chain" / "Full tree") rather than one button whose label doubled as its state. The global **Flatten** toggle is removed: the tree always aggregates repeated siblings, and an analyst expands a `×N` node in place to see its members.

### Fixed

- **Detection alerts are no longer silently lost to a concurrent-processing race.** With concurrent event-batch processing (multiple processor workers per replica since 0.4.0's throughput work, and multi-replica deployments before that), a rule could evaluate an event before the concurrently processed batch carrying that process's fork/exec had committed; the lookup miss was treated as "no finding" and the events were acknowledged, so the alert was permanently dropped with nothing logged. Rule evaluation now fails the batch with a retryable condition when an event's own process is not yet materialized, so the processor re-evaluates it once the row lands (bounded by a 30-second grace window on the event's ingest age, so an event whose process never arrives cannot retry forever). Applies to sudoers tamper, keychain dump, LaunchAgent/LaunchDaemon persistence, DYLD injection, shell-from-Office, osascript network exec, suspicious temp exec, and application-control block alerts.
- **DNS C2 beacon alerts survive that race too, and batch re-processing no longer inflates the process graph or alerts.** The `dns_c2_beacon` correlation now re-evaluates (instead of silently dropping) when the connecting process is not yet materialized, under a tighter grace than the subject-process rules because its resolution runs before the suspicion gate. That retry is only safe because the process-graph builder is now idempotent under re-processing: a batch nack or a claim-lease re-offer that replays the same fork/exec/exit/heartbeat events no longer duplicates process rows (and therefore no longer duplicates alerts, whose dedup keys on the process). Each process row is tied to the events that created and exited it, an exit can no longer close a process that forked after it, and snapshot freshness only advances.
- **The process tree no longer shows a stale collapse chevron during search.** With a search query active, a node whose repeated-sibling group is expanded in place kept drawing a collapsed (`>`) chevron: the glyph was derived from the raw collapsed-id set rather than from what was actually rendered. It now reflects the rendered collapse state, so the chevron matches whether the children are on screen.
- **An alert's process chain no longer renders blank when the alerted process has identical siblings.** The alert graph filters to the alerted process and its lineage, but sibling aggregation (issue #416) folds identical-path leaf siblings into a `×N` node carrying a synthetic id the chain filter cannot match, so an alerted process with even one identical sibling vanished from its own chain (and lost its alert dot). The `GET /api/hosts/{host_id}/tree` endpoint now accepts a `pin` query parameter; the alert view passes the alerted process id so the server keeps that process a first-class node, never folded into an aggregate, and the chain filter and alert dot resolve it by its real id again.

## [0.3.0] (2026-06-26)

Feature release on top of 0.2.1. The headline is operator self-service: detection tuning, single sign-on, API service accounts, and user management all move from boot-time environment variables into governed, audited admin screens that apply without a server restart. Also in this release: a clearer Hosts page, sharper persistence-attribution in alerts, several telemetry-delivery and on-device DNS reliability fixes, and a simpler, safer configuration surface.

### Upgrade notes (action required)

This release retires a number of `EDR_*` environment variables in favor of in-product configuration. Review these before upgrading:

- **Detection tuning is no longer set by environment variables.** The `EDR_*` variables that defined false-positive allowlists and disabled rules are removed. Re-enter any exclusions and per-rule settings through the new Detection settings screen (see Added). This is a hard cutover: suppressions not re-entered will no longer apply.
- **SSO is now configured in-product.** The `EDR_OIDC_*` variables now only seed the configuration on first boot; after that, the stored configuration is the source of truth and is edited from the Single sign-on settings screen.
- **Database connection is configured only via `EDR_DSN` / `EDR_DSN_FILE`.** The separate `EDR_MYSQL_*` variables are removed.
- **22 rarely used tuning variables are removed** and fixed as safe constants. Setting a removed variable is ignored rather than failing boot. The minimum TLS version is now unconditionally TLS 1.3. All security, compliance, and documented operational levers are retained.

### Added

- **Detection tuning moves to a governed admin surface.** View and edit false-positive exclusions and set each detection rule to alert, monitor (evaluate quietly without raising alerts), or disabled, from an audited UI and API. Changes take effect without a server restart and are scoped per host group where applicable.
- **Single sign-on settings screen.** Configure your OIDC identity provider (issuer, client ID and secret, scopes, and default role), test the connection before saving, and apply changes without a server restart. Just-in-time provisioning is always on: anyone who signs in through the provider is auto-created with the default role.
- **API service accounts.** Create non-human principals so automation, CI/release pipelines, and integrations can call the EDR API with a short-lived OAuth client-credentials bearer token instead of a human's browser session. Each account is scoped to a single role, rotated, and revoked from an admin screen, and every lifecycle action and token issuance is audited.
- **In-product user management.** Promote and demote operator roles and enable or disable accounts from a Users screen instead of editing the database by hand, with anti-lockout guardrails (the last admin cannot be demoted, you cannot change your own role, and break-glass users are protected) and an audit row on every change.
- **MITRE ATT&CK coverage map.** A ready-to-share ATT&CK Navigator layer, scoped to the macOS techniques the product detects, ships in the repo for handing to a buyer, auditor, or SOC analyst.
- **Runtime trace-sampling controls.** Tune the server's trace-telemetry volume from an audited admin API without a restart: cap high-frequency agent traffic, lift sampling fleet-wide during an incident-debugging window, and drop health-probe noise entirely. Aggregate latency and alerting keep reading from metrics, which are never sampled, so dialing traces down does not blind your monitoring.

### Changed

- **Redesigned Hosts page.** The page leads with a fleet summary (Online, Offline, and Total host counts) and identifies each machine by hostname and OS version rather than only its raw hardware UUID, so operators can recognize machines at a glance.
- **Single VM is the recommended deployment.** Stand up MySQL, the server, and a Caddy reverse proxy with automatic Let's Encrypt TLS on one operator-controlled VM with a single command. Managed-PaaS edges that run a content-inspecting WAF can silently block agent telemetry, so the supported getting-started path is one where you control the edge.
- **Reduced telemetry bandwidth and on-device overhead.** The agent now compresses uploads (gzip), cutting upload bandwidth several-fold, and repetitive network-connection and DNS-lookup events are coalesced into a single counted event before upload while preserving detection signal. On-device application-control allow decisions are cached at the kernel with safe invalidation on policy change, reducing CPU overhead during heavy process activity.
- **Smaller database footprint.** Per-process liveness heartbeat events (previously a large share of stored rows) are processed for freshness but no longer persisted, and two redundant indexes on the events table are dropped online with no downtime.
- **Fewer false positives from the suspicious-execution rule.** Parent-process allowlist entries now support `*` wildcards so a suppression survives a tool version upgrade, and a lookup to the host's own local DNS resolver no longer counts as a triggering connection. Lookups to public resolvers still fire.
- **Application-control policy changes apply reliably on large fleets.** Saving an application-control policy now pushes the new rules to assigned hosts in batched database writes instead of one write per host, so a change across hundreds or thousands of endpoints commits well inside the request budget instead of risking a timeout and a stuck save.

### Fixed

- **On-device DNS no longer wedges name resolution.** DNS forwarding now has timeouts and a self-healing watchdog that fails open (resolution keeps working) when no blocking policy is active, while still enforcing any active blocks. This fixes an incident where the DNS path could break all name resolution on an endpoint until a reboot, and the break-glass disable command no longer hangs.
- **Clear reboot prompt after a package upgrade.** Network and DNS coverage can stop after upgrading the installed package until the endpoint reboots; the product now surfaces an explicit "reboot required to restore network and DNS coverage" signal instead of an ambiguous warning.
- **Telemetry is retried, not discarded, when the edge rejects uploads.** When a proxy, WAF, edge, or unhealthy origin blanket-rejects uploads (for example with a 403), the agent keeps that telemetry queued and retries until the endpoint recovers, and emits a loud warning and metric so operators see the misconfiguration.
- **Alerts not tied to a single live process now explain themselves.** Persistence and similar alerts no longer open into a blank process graph; they show the alert description and MITRE technique tags with a clear explanation and an opt-in to widen to surrounding host activity.
- **More accurate exclusions and forensic attribution.** Detection exclusions now match correctly regardless of the macOS `/private` path form, so an allowlist you write takes effect; in multi-server deployments every replica picks up detection-config changes within seconds instead of serving stale config; and a network or DNS event from a process that re-launches itself is attributed to the correct generation in the alert timeline.
- **More accessible admin UI status messages.** The single sign-on connection-test result and the account-menu authentication-method badge now meet the WCAG AA color-contrast minimum, and the SSO status banners are emitted as semantic `<output>` live regions so assistive technology announces them.

### Removed

- **Render deployment support.** The one-click Render blueprint (`render.yaml`) and its guide are removed. ## [0.1.1] (2026-06-13)

First stable release. The product ships as two components, released together for now: the **macOS agent** (Apple Silicon, macOS 26+) and the **server** (a Linux container that runs anywhere containers do, cloud or on-prem). Core capabilities:

- **Real-time macOS endpoint monitoring.** An Endpoint Security system extension and a network extension capture process execution, fork/exit, file access, DNS queries, network connections, and background-task (launch item) registration, streamed continuously to the server.
- **Live process-graph correlation.** The server reconstructs a per-host process tree, including parent/child lineage and re-exec chains, so every alert carries the full process ancestry that led to it.
- **Out-of-the-box detection rules.** A catalog of behavioral detections covering credential access (keychain dumping), persistence (launch agents and daemons), privilege escalation (sudoers and launchd tampering), process injection (DYLD insertion), command-and-control beaconing, and suspicious execution chains.
- **Cross-stream correlation.** Rules reason over execution, DNS, and network together, catching multi-step behavior a single-signal tool misses, such as a process that beacons to a suspicious domain and then connects out.
- **Application control.** Block execution on the endpoint by binary hash, path, CDHash, signing ID, team ID, or leaf certificate, enforced at exec time before the process runs.
- **Process response.** Kill a running process on a host on demand from the server.
- **Tunable allowlists.** Per-rule allowlists suppress known-good management tooling, such as MDM agents that drop launch daemons or write sudoers, so legitimate activity does not generate noise.
- **Operator web UI.** Browse hosts, drill into process trees, triage and comment on alerts, and manage application-control policy.
- **SSO and break-glass authentication.** OIDC single sign-on with just-in-time user provisioning, plus a WebAuthn passkey break-glass path for recovery when SSO is unavailable.
- **Role-based access control.** Five built-in roles (super admin, admin, senior analyst, analyst, auditor) enforced through a single authorization chokepoint that no privileged action can bypass.
- **Append-only audit log.** Every privileged action and authorization decision is recorded immutably for later review.
- **Offline-tolerant agent.** A durable on-device SQLite queue buffers events when the server is unreachable and uploads them on reconnect, so nothing is lost during an outage.
- **Built to scale.** A stateless server runs as multiple replicas behind a load balancer, drains gracefully on deploy, applies schema migrations automatically, and enforces configurable event retention.
- **Flexible deployment.** The server is a standard Linux container image, so it runs on any container host (a Docker VM, Kubernetes, AWS ECS/EKS, GCP, Azure, or on-prem), with a one-click Render blueprint for the fastest start. Agents reach Macs through any MDM (Fleet, Jamf, Kandji, Intune, mosyle).
- **Supply-chain-hardened releases.** Every release ships a Developer ID-signed, Apple-notarized package alongside SBOMs, cosign signatures, and build provenance attestations.
